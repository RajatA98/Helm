## 🔳 Codex - gpt-5.5
**Recommendation**

Choose **C: SwiftUI native shell + bundled Three.js in `WKWebView`**.

It is the best fit for Helm because it protects the thing you already love: the working ship-at-sea prototype. You get native SwiftUI for the parts that must feel instant and Apple-y, while avoiding a risky shader rewrite before the product has proven itself.

Use this shape:

```text
SwiftUI app
  Today dock, task log, sheets, settings, friends, auth, sync
  SwiftData/local cache for instant launch + offline check-offs
  WKWebView full-screen 3D scene, bundled with app
    Receives state: hull %, leaks, heading, time of day, goal islands
    Sends events: wheel tapped, island selected, barrel tapped
```

Keep the 3D scene as a **view layer only**. No authoritative task state, friend state, ledger state, auth, or sync logic should live in JavaScript.

Apple’s SceneKit deprecation makes “rebuild it in SceneKit” a poor bet; Apple now points SceneKit users toward RealityKit. Expo is viable, but Expo’s own docs still call Expo Go limited for production-grade apps with native needs, and `expo-gl` has real limitations around debugging, native crashes from invalid GL usage, and incomplete WebGL2 APIs. For this app, React Native gives you TypeScript comfort but makes the Apple ecosystem story worse.

Sources: Apple SceneKit docs, Apple CloudKit docs, Expo GL docs, Expo dev-build docs.  
https://developer.apple.com/documentation/SceneKit  
https://docs.expo.dev/versions/latest/sdk/gl-view/  
https://docs.expo.dev/develop/development-builds/faq/

**Biggest Risks Of Option C**

1. **WKWebView 3D performance may be “good enough” but not native-good.**  
   Test early on real devices, especially older iPhones. Your first milestone should be: 60-ish FPS target, acceptable battery/thermal behavior, fast resume, no memory spikes.

2. **The native/WebView bridge can become messy.**  
   Define a tiny message protocol now. Version it. Treat it like an API.

```swift
struct SceneState: Codable {
    let hullPercent: Double
    let leaks: Int
    let heading: Double
    let timeOfDay: String
    let activeGoalId: String?
}

webView.evaluateJavaScript("""
window.helmScene?.setState(\(jsonString));
""")
```

```js
window.webkit.messageHandlers.helm.postMessage({
  type: "wheelTapped",
  goalId: activeGoalId,
  version: 1
});
```

3. **You now have two UI runtimes.**  
   SwiftUI and Three.js will each have lifecycle bugs: app backgrounding, memory warnings, dark mode, rotation, network-offline state, asset loading. Keep the WebView dumb and replaceable.

4. **Mac app quality depends on discipline.**  
   SwiftUI multiplatform helps, but a `WKWebView` scene on Mac still needs tuning for window sizes, input, and performance. Better than React Native’s iPad-on-Mac story, but not free.

5. **Future RealityKit migration is possible, not automatic.**  
   You are buying time. That is okay. To preserve the option, keep the scene API declarative: `setState`, `playEvent`, `setCamera`, `selectGoal`. Do not let native code know Three.js internals.

**Backend Recommendation**

Use **Supabase + native SwiftData local cache**.

For Helm’s actual requirements, Supabase is the most practical backend:

- friends/crew data across accounts
- shared rules and IOU ledger
- Sign in with Apple
- private photo proof storage
- server-side LLM calls
- scheduled midnight “missed task → leak” job
- minimal ops
- AI-friendly TypeScript/SQL development

Supabase gives you Postgres, Row Level Security, Storage, Edge Functions, and Cron/scheduled functions. That maps cleanly to Helm. Supabase’s docs explicitly support scheduled Edge Functions via cron.  
https://supabase.com/docs/guides/functions/schedule-functions  
https://supabase.com/docs/guides/cron

Use SwiftData for instant local UX:

```text
SwiftData local store
  tasks
  goals
  checkoffs
  pending_sync_events

Supabase
  users
  crews
  crew_members
  goals
  tasks
  checkoffs
  leaks
  ious
  proof_photos
```

For offline check-offs, do not overbuild sync. Use a simple outbox:

```text
User checks off task offline
→ write Checkoff locally
→ append PendingSyncEvent
→ update UI immediately
→ when online, POST event to Supabase
→ server applies idempotently
```

Make each event idempotent with a UUID:

```sql
create table checkoffs (
  id uuid primary key,
  user_id uuid not null,
  task_id uuid not null,
  completed_at timestamptz not null,
  created_at timestamptz default now()
);
```

**Why Not CloudKit First?**

CloudKit is excellent for Apple-only private sync and shared records, and it has native push-style sync subscriptions. But Helm needs backend behavior: scheduled jobs, server-side LLM calls, friend nudges, ledgers, moderation/privacy controls around photos, and eventually friend-group mechanics. CloudKit can be made to work, but you will spend more energy fighting product-shaped backend needs.

CloudKit is the right choice only if you decide: “This is a personal Apple-only app first, social/backend features later.”

**Why Not Firebase?**

Firebase is also a strong choice, especially for offline sync, push, and scheduled functions. Firestore has built-in offline persistence on Apple platforms, and Cloud Functions support scheduled jobs.  
https://firebase.google.com/docs/firestore/manage-data/enable-offline  
https://firebase.google.com/docs/functions

But for Helm’s IOU ledger, crew rules, sharing model, and future reporting, Postgres is a better long-term fit. Supabase will also be easier for AI tools to reason about because the schema and policies are explicit SQL.

**Final Call**

Build Helm as:

```text
SwiftUI + SwiftData + WKWebView/Three.js + Supabase
```

That is the pragmatic portfolio-quality stack. It keeps the magical 3D prototype, gives you native Apple screens, supports a real backend, and avoids going “super all out” before you know which parts of Helm will actually stick.
