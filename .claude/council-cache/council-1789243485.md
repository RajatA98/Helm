## 🔳 Codex - gpt-5.5
Overall: the plan is strong, but it is too backend-heavy too early, and Phase 4 is dangerously large. The riskiest part is that the “actual daily accountability loop” could get buried under sync, AI onboarding, crews, RLS, pushes, and polish before the core habit engine has proven itself emotionally useful.

I would keep the broad order, but split and resequence it.

**Verdict**

The right spine is:

1. Ship scene in app
2. Local daily loop
3. Cloud backup/account restore
4. Onboarding/maps
5. Crews/social
6. Polish/TestFlight/demo

But the current version has two problems:

- Phase 3 introduces full offline sync, server rollover, RLS, storage, auth, and cron before you know whether the solo daily loop is compelling.
- Phase 4 combines onboarding, AI planning, map editing, charts, manual editing, weekly review, route rebuilds, avatar creation, notification setup, and first-launch UX. That is not one phase. That is probably three.

The project will most likely go wrong by overbuilding the “platform” before validating the daily behavior.

## Phase-By-Phase Review

**Phase 1: The ship inside the app**

Good phase. Keep it.

This is the right first move because the live ship is the product’s emotional center and the biggest technical unknown: SwiftUI + `WKWebView` + Three.js + bridge messages + performance.

I would add these acceptance criteria:

- Bridge messages are logged/versioned and ignored safely when unknown.
- Scene can render from a deterministic mock `ShipState`.
- App can run with scene unavailable or failed to load.
- Memory/battery smoke test after 5-10 minutes on device.
- Web assets are bundled, cacheable, and do not depend on network.

Also: do not let Phase 1 become “make the ship beautiful.” It only needs to prove the architecture and emotional promise.

**Keep. Maybe timebox hard.**

---

**Phase 2: The daily loop, on one phone**

This is the most important phase. It should be bigger than Phase 1 and should probably last until you personally use it for at least 7-14 days.

The scope is mostly right, but I would cut or defer:

- “pre-written crewmate line library for 5 crewmates” can be smaller.
- “Add photo” can start as local proof attachment, but do not over-polish proof UX.
- temporary hand-entry is fine, but make it good enough to use, not a throwaway mess.

What is missing:

- A manual “repair bad rollover” or debug/admin screen for the builder.
- A deterministic rules test fixture system.
- A clear “source of truth” for hull events: do not only store current hull. Store the events that caused it.
- Explicit task identity and recurrence identity. Recurring tasks get messy fast.
- Data export/debug dump, even if ugly.

Your rules engine needs to be boring, deterministic, and heavily tested. The ship can be whimsical; the rules engine should be accounting software.

**Keep, but treat this as the product validation phase.**

---

**Phase 3: Accounts and the cloud**

This phase is too big and too early as written.

I would split it:

**Phase 3A: Backup and restore only**

- Supabase project
- schema
- Auth
- RLS
- basic sync upload/download
- reinstall restore
- private photo storage if proof is already important

Acceptance:

- one user can reinstall and recover data
- RLS prevents cross-user reads
- duplicate uploads do not duplicate records
- sync failure does not corrupt local data

**Phase 3B: Multi-device/server rollover later**

Server rollover across time zones is much harder than it looks. You now have two possible authorities: the phone and the server. That invites duplicate leaks, missed leaks, and “why did my ship sink while I was offline?” moments.

For an iPhone-first solo/friend app, I would initially make the device the primary rollover authority and let the server reconcile event logs. Add server cron only when crews depend on timely shared visibility.

If you keep server rollover in Phase 3, you need a very explicit idempotency model:

```text
rollover_event_id = user_id + local_date + timezone + goal/task_scope
```

And every hull/leak mutation should be safely repeatable.

**Resequence. Start with backup/restore, defer authoritative cron.**

---

**Phase 4: The Navigator, onboarding and maps**

This is the most overloaded phase.

It contains:

- first-launch experience
- sign-in
- avatar creator
- AI goal conversation
- structured map generation
- map review/edit
- charts/table screens
- treasure map
- island detail
- manual editing
- notification setup
- invite placeholder
- island-reached moment
- Sunday review
- route rebuild
- AI spend cap

That is too much.

I would split it into:

**Phase 4A: Manual maps and editing**

Before AI, build the map model and screens manually:

- create/edit goal
- create/edit islands/checkpoints/tasks
- Today dock reflects real map
- island reached works
- chart/table works

This proves the data model without AI ambiguity.

**Phase 4B: Navigator onboarding**

Then add AI to produce a draft map, not directly mutate saved state.

Acceptance:

- AI output always becomes a reviewable draft
- malformed output is rejected
- user can edit before save
- prompt/version stored with generated plan
- cost cap works

**Phase 4C: Sunday review and route rebuild**

This should come after you have at least one real week of usage. Weekly review is central, but it depends on the daily loop being real.

**Big recommendation: do manual map creation before AI map creation.**

AI should accelerate a workflow that already exists. It should not define the first version of the workflow.

---

**Phase 5: Crews, the Cove and TestFlight**

This is also large, but the order is mostly right.

However, I would move TestFlight earlier.

You do not need crews to justify TestFlight. You need TestFlight as soon as the roommate is going to use it on their actual phone with real data. Sideloading with a free Apple ID is fine for you, but it becomes friction quickly.

Suggested change:

- Move Apple Developer account + TestFlight setup to the end of Phase 3 or start of Phase 4.
- Keep crews/social features in Phase 5.

Also, replacing OTP with Sign in with Apple in Phase 5 may cause auth migration pain. If you know iOS-only/TestFlight is the path, consider using Sign in with Apple earlier, or support account linking explicitly.

The Code/unanimous acceptance/IOU ledger is high-risk product complexity. I would narrow the first crew version:

- crew invite/join
- hull/status visibility
- nudges
- sinking alert
- no IOU ledger yet, or ledger as manual notes only

The IOU ledger can change the vibe from “accountability game” to “social debt app.” Useful maybe, but risky.

**Keep crews after solo loop + cloud, but move TestFlight earlier and shrink first crew scope.**

---

**Phase 6: Polish and demo-ready**

Good final phase, but accessibility/account deletion should not wait entirely until Phase 6.

Account deletion especially should arrive with accounts/cloud. If you are storing personal goals/photos, make deletion part of Phase 3 or Phase 5 at latest.

Accessibility should be considered during implementation, then audited in Phase 6. If you wait until the end, VoiceOver and Dynamic Type may fight your layout architecture.

Performance/battery also should be checked in every phase, not saved for polish.

**Keep final polish, but pull privacy/account deletion and baseline accessibility earlier.**

## What’s Missing

**1. A data/event architecture phase**

You need an explicit event model before sync.

For example:

```swift
enum ShipEventType {
    case taskCompleted
    case taskCompletionUndone
    case leakCreated
    case leakPatched
    case perfectDayAwarded
    case shipSank
    case shipRaised
}
```

Store events with UUIDs, local dates, timezone, created timestamps, and sync status. Derive hull from events, or at least keep events as the audit trail.

This will save you when sync, cron, undo, weekly quotas, and crews arrive.

**2. Conflict strategy**

Offline-first sounds simple until two devices or server cron touch the same logical day.

Decide now:

- Is one user expected to use multiple devices?
- What wins if local and server both produce rollover events?
- Can checkoffs be undone after sync?
- Is “until midnight” based on the user’s current timezone or the timezone when the task was scheduled?

**3. Observability/debugging**

For an AI-assisted solo build, you need visible debugging tools:

- current local date/time interpretation
- due tasks
- pending outbox items
- last sync result
- raw hull events
- bridge messages
- notification schedule
- AI request cost/log ID

This does not need to be pretty. It will save the project.

**4. Privacy and safety basics**

Goals and photos can be sensitive.

Add:

- account deletion
- photo deletion
- crew visibility preview: “what allies can see”
- RLS tests
- storage access tests
- no AI access to proof photos unless explicitly intended

**5. Notification strategy**

“Max 3 local reminders/day” is good, but you need a policy:

- What are the 3 slots?
- Are they user-chosen?
- Do overdue/leak/crew notifications count?
- What happens when Focus mode suppresses them?
- Are Sunday review reminders separate?

**6. AI fallback**

Navigator should not block onboarding.

If Claude/Supabase Edge Function fails, user should be able to create a simple starter map manually.

- route rebuild sophistication

Keep the magic concentrated: ship, hull, leaks, islands, roommate accountability.

## Recommended Resequenced Plan

**Phase 1: Ship Shell**

Same as yours. Prove WKWebView, bridge, rendering, taps, pause/resume, local-time sky.

**Phase 2: Local Accountability Engine**

SwiftData, event log, recurrence rules, hull/leak math, checkoff/undo, proof photos, local notifications, debug panel, real daily usage.

**Phase 3: Manual Maps + Real Editing**

Create/edit goals, islands, checkpoints, tasks, chart table, island detail, map progression. No AI yet.

**Phase 4: Cloud Backup + TestFlight Foundation**

Supabase schema/RLS/Auth, backup/restore, outbox sync, private storage, account deletion, TestFlight setup. Keep server cron optional or limited.

**Phase 5: Navigator**

AI onboarding creates draft maps; map review/edit; Sunday review; route rebuild; cost caps; malformed output handling.

**Phase 6: Crews + Cove**

Invite/join, one crew per user, visibility enforcement, nudges, ship status, Code acceptance. Defer IOU ledger unless the friend group specifically wants it.

**Phase 7: Polish + Demo**

Moments, accessibility audit, battery/performance, visual upgrades, App Store/TestFlight presentation, demo recording.

If you want to keep exactly 6 phases, merge Manual Maps into Phase 2 or 4, but I think making it explicit is worth it.

## Highest-Risk Failure Points

**1. Recurrence rules and rollovers**

Midnight, DST, weekly quotas, travel, undo-until-midnight, server cron, and offline mode are a nasty cluster. This is where hidden bugs will live.

**2. Sync idempotency**

“Airplane-mode strikes sync without duplicates” is the right criterion, but you need event IDs and unique constraints everywhere. Otherwise duplicate hull damage will happen.

**3. Phase 4 scope explosion**

Navigator + onboarding + maps + review + charts + editing is the phase most likely to sprawl.

**4. Social pressure mechanics**

Sinking alerts and IOUs can be motivating or stressful. With roommates/friends, tone matters. Start softer than you think.

**5. WKWebView performance/battery**

A beautiful full-screen Three.js scene can quietly burn battery. Keep a low-power mode early.

**6. AI output trust**

Never let AI write directly into durable user state. AI should produce drafts, and your app should validate them like untrusted input.

---

## Honest Bottom Line

The concept is excellent, and the first two phases are pointed in the right direction. The main change I’d make is this:

Build the local product and manual map system before making it cloud/social/AI-heavy.

Your north star should be: “Can I use Helm every day for two weeks and feel the ship changing my behavior?” If yes, Supabase, Navigator, crews, and polish are worth the climb. If no, those layers will only make the wrong product harder to change.
